# Interest engine, stories migration, onboarding flow, and voice note upload

Four features land in one batch: a client-side feed ranking engine driven by Firestore interest vectors, a Supabase→Firestore migration for the stories pipeline, a three-step onboarding wizard that seeds the interest engine, and a voice-note upload fix that replaces a dead Supabase shim with Cloudinary. The approach is consistent — lean on Firestore documents, keep ranking logic client-side, and use Cloudinary for all binary media. Watch for: race condition in `updateInterestVector` that can lose writes under concurrent engagement signals (confirmed), the scoring formula producing zero scores for brand-new posts with no engagement (confirmed), sequential Firestore writes in onboarding completion creating a partial-write failure window (confirmed), and `hasUnseen` on StoriesRail being hardcoded to `true` which defeats the StoryRing's seen/unseen distinction (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The interest engine introduces a read-modify-write pattern on `user_interests/{userId}` that is not atomic — two concurrent likes on posts tagged "Art" will race through `getDoc → setDoc` and one delta will be lost. The pure `scorePosts` function multiplies by engagement velocity, which is zero when a post has no likes or comments, so fresh content sinks to the bottom of "For You" until someone else engages first.

The stories migration removes Supabase from `StoryCompose` and `StoryViewer`, replacing it with Firestore `addDoc`/`updateDoc` calls. Reactions use `arrayUnion` which avoids duplicates by value — but since each reaction object includes a timestamp, the same user can react with the same emoji multiple times because the objects are never truly equal.

Onboarding writes interests, follows, and profile updates in sequence without a batch. If step 3 (`updateDoc` on the profile) succeeds but some follow-writes in the loop failed, the user is considered onboarded and will never be prompted to re-follow. When no creators exist in Firestore, the "Continue" button is enabled so users bypass the follow minimum entirely — acceptable but undocumented.

The Cloudinary module uses an unsigned upload preset with a hardcoded fallback cloud name, so any environment without `VITE_CLOUDINARY_CLOUD_NAME` silently uploads media to a foreign Cloudinary account. Now that voice notes actively use this path, the risk surface is wider.

<details>
<summary>Issues (7)</summary>

1. **Interest vector race condition** — `updateInterestVector` does get-then-set without a transaction; concurrent signals on the same user lose deltas. Wrap in a Firestore transaction or use `increment()`.
2. **Zero-engagement posts score zero** — `scorePosts` multiplies by engagement velocity, which is 0 when `like_count` and `comment_count` are both 0. Add a floor (e.g., `Math.max(1, ...)` or add 1 before dividing).
3. **Duplicate emoji reactions** — `arrayUnion` compares by deep equality, but each reaction includes a unique `created_at` timestamp, so duplicate reactions from the same user are never deduplicated. Remove `created_at` from the reaction object or deduplicate on `user_id + emoji` before writing.
4. **Onboarding partial-write window** — Sequential `setDoc`, loop of `addDoc`, and `updateDoc` without a batch mean a mid-sequence failure can leave follow data incomplete while the profile is marked onboarded. Use a `writeBatch`.
5. **`hasUnseen` always true** — `StoriesRail` passes `hasUnseen={true}` to every `StoryRing`, so the gradient ring never falls back to grey. Pass actual seen state from the viewer tracking data.
6. **Hardcoded Cloudinary fallback** — `cloudinary.ts` uses `"dxoqepdck"` and `"ml_default"` when env vars are missing, silently uploading to a foreign account. Throw at startup if the vars are absent, or remove the fallback.
7. **Feed re-fetches on every tab switch** — `load()` fires on every `tab` change via `useEffect`, issuing a new Firestore read and interest vector fetch each time. Cache the post list or debounce tab switches.

## Interest vector: race condition and scoring edge case

`updateInterestVector` reads the document, spreads the existing map, increments one key, and writes back:

```ts
const snap = await getDoc(docRef);
const data = snap.data() as InterestVector;
await setDoc(docRef, { ...data, [topic]: current + delta }, { merge: true });
```

Two near-simultaneous calls (e.g., user rapid-fires likes on two posts) will both read the same snapshot and one write will silently overwrite the other's delta. Firestore transactions exist precisely for this — wrap the read-modify-write in `runTransaction`, or better yet use `FieldValue.increment(delta)` in a single `updateDoc` call which is atomic and cheaper.

The scoring formula multiplies three factors: `contentTopicMatch * recencyFactor * engagementVelocity`. Engagement velocity is `(like_count + comment_count * 2) / max(1, hoursSincePost)`. A brand-new post with 0 likes and 0 comments gets velocity = 0, making the entire product 0 regardless of topic match. This creates a cold-start problem: posts need external engagement before the algorithm will surface them. A minimal fix is `max(1, like_count + comment_count * 2)` so topic affinity and recency still drive ranking for fresh content.

## Stories: reaction deduplication gap

`StoryViewer.react()` appends to the reactions array:

```ts
reactions: arrayUnion({ user_id: user.uid, emoji, created_at: new Date().toISOString() })
```

`arrayUnion` deduplicates by exact object equality. Because `created_at` differs on every call, a user tapping ❤️ three times produces three separate reaction entries. The pragmatic fix is to remove `created_at` from the reaction object or deduplicate on `user_id + emoji` before writing. Client-side debounce (disable button after first tap per emoji) would also work but doesn't protect against replayed requests.

## Onboarding: partial-write and routing asymmetry

`handleComplete` performs these writes in sequence: (1) `setDoc` to `user_interests/{userId}`, (2) N × `addDoc` to `follows`, (3) `updateDoc` on `profiles/{userId}` with `onboarded_at` and `interests` array. If step 3 succeeds but some follows in step 2 failed silently, the user is marked onboarded with incomplete follow data and will never be re-prompted. Wrapping all writes in a `writeBatch` would eliminate this gap.

The step-2 disable logic:

```ts
disabled={(step === 2 && !canProceedStep2 && creators.length > 0)}
```

When `creators.length === 0`, the button is enabled regardless of `canProceedStep2`. Users in a fresh environment with no `is_creator` profiles bypass the follow minimum entirely.

## Feed ranking: redundant fetches and tab asymmetry

The `useEffect` dependency array is `[tab, user?.id]`, so switching tabs triggers a full re-fetch including the Firestore posts query and interest vector read. For a mobile app with frequent tab toggles this will produce noticeable latency and unnecessary Firestore reads. Caching the fetched posts and only re-ranking on tab switch would reduce reads substantially.

Both tabs share the same Firestore query (no follower filter), so "following" currently shows the same content as "for you" minus the reordering — the tab distinction is cosmetic.

## Cloudinary fallback credential risk

```ts
const CLOUD_NAME = import.meta.env.VITE_CLOUDINARY_CLOUD_NAME || "dxoqepdck";
const UPLOAD_PRESET = import.meta.env.VITE_CLOUDINARY_UPLOAD_PRESET || "ml_default";
```

This is a pre-existing pattern, but now that voice notes, stories, and onboarding avatars all route through `uploadToCloudinary`, any deployed instance without env vars silently uploads user media to an account the project may not control. Fail loudly at build time or module init.

## Test coverage gaps

Not tested: `updateInterestVector` atomicity, `scorePosts` with zero-engagement posts, `VoiceRecorder.send()` (the actual upload path), onboarding `handleComplete` write sequence, story reaction deduplication behavior.
