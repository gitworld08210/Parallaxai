# Monetization features: coin purchases, tipping, analytics, scheduling, live gifts

Five monetization features migrated to Firebase Firestore with client-side `runTransaction` for atomic wallet operations. The coin purchase flow writes to `coin_purchases` and transitions from `pending` → `submitted` on UTR entry; admin approves in a new Finance Department page. Tipping and live-stream gifting use `runTransaction` to read-then-debit-then-credit in a single atomic pass, preventing double-spend. Self-transfer guards block tipping yourself and gifting your own stream. The Analytics page queries Firestore aggregations client-side with recharts charting, and Drafts was rewritten from Supabase to Firestore queries.

Watch for: wallet rules allow any authenticated user to credit any wallet (**confirmed**), coin purchase approval is non-atomic with the wallet credit (**confirmed**), live-stream `total_gifts` update can diverge from the actual gift ledger (**confirmed**).

**Verdict**: NEEDS_CHANGES

## High-level view

The wallet security model is acknowledged as temporary (TODO comments throughout), but the Firestore rules as shipped allow any authenticated user to update any wallet document. A malicious client can bypass the UI's `runTransaction` and call `updateDoc` on any wallet with an arbitrary balance. The rule `allow update: if request.auth != null` on wallets provides no server-enforced security boundary.

The Finance Department approval page credits coins via a bare `updateDoc(walletRef, { total: increment(coins) })` — separate from the status update on `coin_purchases`. If the `increment` call fails after the status write succeeds, coins are lost; if retried, coins double. The ApprovalsInbox page already uses `runTransaction` for its approval flow, making this inconsistency easy to fix.

Tipping and live gifting correctly wrap the debit + credit inside `runTransaction` and include self-transfer guards. The transaction log (`addDoc` to `transactions` / `live_gifts`) happens outside the transaction, so a failure there creates a silent gap in the ledger without rolling back the balance change.

The analytics hook fires unbounded Firestore queries that require composite indexes to function. Without them, the queries will be rejected and the user sees an empty dashboard with no error feedback.

<details>
<summary>Issues (5)</summary>

1. **Wallet rules allow arbitrary credits** — `allow update: if request.auth != null` on `wallets/{walletId}` means any authenticated user can set any wallet to any balance. Add a Cloud Function or restrict the rule to owner-only debits until a server-side transfer endpoint exists.
2. **FinanceDepartment non-atomic approval** — `handleApprove` updates `coin_purchases` status and then calls `increment` on the wallet as a separate write. Use `runTransaction` (matching ApprovalsInbox pattern) or move to a server function.
3. **Gift and transaction ledger outside transaction boundary** — The `addDoc` to `live_gifts` and `transactions` occurs after the wallet `runTransaction` commits. A failure means the wallet was debited/credited but no record exists. Move the ledger write inside the transaction, or accept the gap and document it.
4. **`total_gifts` on `live_streams` diverges from ledger** — `updateDoc(doc(db, "live_streams", streamId), { total_gifts: increment(g.cost_coins) })` is a separate write from the gift transaction. A failure leaves the counter stale; a retry could double it.
5. **`coin_purchases` rules allow any user to update any purchase** — `allow update: if request.auth != null` means a malicious client could set their own purchase to `"approved"` status. The actual coin crediting won't happen (it's triggered by admin action), but the status field has no server-enforced constraint.

## Wallet transfer atomicity vs. authorization

The security boundary problem is the Firestore rule:

```
match /wallets/{walletId} {
  allow update: if request.auth != null;
}
```

A malicious client can skip the `runTransaction` entirely and call `updateDoc(doc(db, "wallets", victimId), { total: 999999 })`. The TODO comments acknowledge this and say "move to Cloud Functions for production." This is the single most important item to close before a public launch — anyone who reads the rules file (which is committed to the repo) has the attack vector.

The `coin_purchases` collection has the same open-update rule. Although the wallet isn't credited by updating the purchase status (it requires admin action in the Finance page), a client could mark their own purchase as "approved" to create confusion. Restrict updates to `status == "submitted"` transitions only from the owner, and terminal states from admin custom claims.

## Finance Department approval race

`FinanceDepartment.handleApprove` performs two sequential writes:

```ts
await updateDoc(doc(db, "coin_purchases", req.id), { status: "approved", ... });
await updateDoc(doc(db, "wallets", req.user_id), { total: increment(req.coins) });
```

Contrast with `ApprovalsInbox.handleApproveTopup`, which wraps both in `runTransaction`. The Finance Department page is the one surfaced to reviewers for coin purchases, yet it lacks the atomic guarantee. If the second write fails (network interruption, permission error), the purchase is marked approved but no coins arrive. If the admin retries (the request is already filtered from the "submitted" query, so this requires developer tools), coins double.

## Ledger writes outside transaction

In `useTipSend`:
```ts
await runTransaction(db, async (transaction) => { /* debit + credit */ });
await addDoc(collection(db, "transactions"), { ... }); // outside
```

In `LiveViewer.sendGift`:
```ts
await runTransaction(db, async (transaction) => { /* debit + credit */ });
await addDoc(collection(db, "live_gifts"), { ... }); // outside
await updateDoc(doc(db, "live_streams", stream.id), { total_gifts: increment(...) }); // outside
```

The `total_gifts` write is particularly fragile: `increment` is not idempotent across retries if the outer code doesn't deduplicate. A transient network error after the balance transaction commits leads to either a missed increment (gift counter is low) or — if the UI retries the whole flow — a second debit + credit on a new transaction.

## Analytics missing composite indexes

`useCreatorAnalytics` issues three Firestore queries that combine `where` + `orderBy` on different fields:
- `follows` filtered on `following_id` and `created_at`
- `transactions` filtered on `recipient_id`, `type`, and `created_at`

Firestore requires an explicit composite index for each of these. Without them, the SDK throws and the `catch` block logs a warning but shows no user-facing error. A new deployment will produce an empty analytics dashboard until the indexes are created.

## Test coverage gaps

Tests exist for TipSheet, BuyCoinsSheet, Analytics, Drafts, and LiveHost. They verify rendering with mocked Firestore calls.

Not tested: the `runTransaction` wallet debit/credit logic in `useTipSend`, the self-transfer guard rejection path, the `sendGift` and `buyTicket` flows in LiveViewer, the Finance Department approve/reject flow, or any failure-path behavior (insufficient balance, network errors during transaction, partial write failures).
