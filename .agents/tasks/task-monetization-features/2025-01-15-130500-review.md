# Monetization features: coin purchases, tipping, live gifts, analytics, and drafts migration

Five features land together: manual coin purchase with admin approval, wallet-to-wallet tipping, live-stream gifting, creator analytics, and a Supabase-to-Firebase migration for drafts/scheduling. All wallet operations (tips, gifts, ticket purchases) follow the same client-side pattern: read balance → check sufficiency → decrement sender → increment recipient → log transaction. Every one of these flows is broken by the existing Firestore security rules, which restrict wallet writes to the document owner — meaning the recipient credit step will be rejected in production.

Watch for:
- **Wallet writes will fail in production** — Firestore rules only allow the wallet owner to write their own wallet document, so crediting a recipient from the sender's client is denied (confirmed).
- **Race condition on balance checks** — read-then-write without transactions allows double-spend under concurrent requests (confirmed).
- **No self-tip or self-gift guard** — a user can tip themselves and inflate analytics earnings totals (confirmed).
- **Finance admin page has no Firestore-level authorization** — any authenticated user who navigates to `/admin-os/finance` can approve purchases and credit wallets (likely, given missing rules for `coin_purchases`).

**Verdict**: NEEDS_CHANGES

## High-level view

All wallet transfer logic lives in the client (useTipSend, LiveViewer.sendGift, LiveViewer.buyTicket, FinanceDepartment.handleApprove). The pattern is always getDoc → check balance → updateDoc with increment. This is fundamentally at odds with the deployed Firestore security rules, which only let `request.auth.uid == walletId` write to `/wallets/{walletId}`. The recipient credit will throw a permissions error on every tip, gift, and ticket purchase.

Even if the rules were relaxed, the read-then-write pattern has a textbook TOCTOU race: two concurrent tips can both read "sufficient balance" and both deduct, driving the balance negative. Firestore transactions (the `runTransaction` API) exist precisely for this, wrapping the read and write in an atomic unit with optimistic concurrency.

The Finance Department page is gated at the React routing level by `AdminOSGate` (which checks `profile.is_admin` or org account type), but the Firestore rules file has no entry for `coin_purchases` — meaning any authenticated client can read, write, update, or delete purchase records directly. The admin approval action (marking status as "approved" and crediting the wallet) could be replayed by a non-admin who crafts the right Firestore call.

The analytics hook and drafts migration are straightforward Firestore query rewrites with proper cancellation semantics. No wallet operations or security-sensitive logic involved.

<details>
<summary>Issues (5)</summary>

1. **Recipient wallet credit blocked by security rules** — The wallet security rule (`resource.data.user_id == request.auth.uid`) prevents one user from writing another user's wallet. Every tip, gift, and ticket purchase will fail in production. Move wallet transfer logic to a Cloud Function or update rules to allow increment-only writes via a validated transaction path.
2. **Double-spend via read-then-write race** — `useTipSend`, `sendGift`, and `buyTicket` all read balance with `getDoc` then write with `updateDoc(increment(...))` in separate operations. Two concurrent calls can both pass the balance check. Wrap the read+write in a Firestore `runTransaction` to get atomic compare-and-set.
3. **Self-transfer not prevented** — Nothing stops `senderId === recipientId` in `useTipSend` or `me === stream.host_id` in `sendGift`. A self-transfer leaves net balance unchanged but creates a spurious transaction record (and in the gift case, inflates `total_gifts`). Add a guard before the transfer.
4. **Finance page lacks Firestore-level access control** — `coin_purchases` has no security rule entry, defaulting to deny-all in production (good) or open in development emulators. If using permissive dev rules, any authenticated user can approve their own purchase. Add explicit admin-only rules for this collection.
5. **BuyCoinsSheet UTR submission doesn't update status** — After writing `utr_number`, the document stays in `status: "pending"`. The admin sees requests whether UTR is submitted or not. If intentional, consider filtering in the Finance UI to distinguish "awaiting UTR" from "UTR submitted, awaiting review".

## Client-side wallet transfers versus Firestore rules

The wallet collection rule in `firestore.rules` is:

```
match /wallets/{walletId} {
  allow read: if request.auth != null && resource.data.user_id == request.auth.uid;
  allow write: if request.auth != null && request.resource.data.user_id == request.auth.uid;
}
```

Every transfer flow calls `updateDoc(doc(db, "wallets", recipientId), { total: increment(amount) })` from the sender's authenticated session. Since `request.auth.uid` is the sender and the wallet document's `user_id` is the recipient, the write is denied.

This affects:
- `useTipSend` (line 39: credit recipient wallet)
- `LiveViewer.sendGift` (credit host wallet)
- `LiveViewer.buyTicket` (credit host wallet)
- `FinanceDepartment.handleApprove` (credit user wallet from admin session)

The fix is either to move transfer logic server-side (a Firebase Cloud Function that validates and performs the atomic transfer) or to restructure rules with a custom claim check. A Cloud Function is the standard approach for financial operations because it also solves the race condition.

## TOCTOU race in balance checks

```typescript
// useTipSend.ts
const senderSnap = await getDoc(senderWalletRef);
const currentBalance = senderSnap.exists() ? (senderSnap.data().total || 0) : 0;
if (currentBalance < amount) { ... }
// ← another tab/device can deduct here
await updateDoc(senderWalletRef, { total: increment(-amount) });
```

The `getDoc` and `updateDoc` are not atomic. If a user opens two tabs and tips simultaneously, both reads see sufficient balance, both decrements succeed, and the balance goes negative. Firestore's `runTransaction` performs an optimistic lock: it retries if the document changed between read and write. Even without moving to a Cloud Function, wrapping the existing client logic in `runTransaction` would close this gap.

The same pattern repeats identically in `sendGift` and `buyTicket` in LiveViewer.

## Missing self-transfer guard

In `useTipSend`, `senderId` and `recipientId` are both passed from the UI. The TipSheet passes `user.id` as `senderId` and the content creator's ID as `recipientId`, but nothing validates `senderId !== recipientId`. A user viewing their own reel could tap the tip button and transfer coins to themselves — the increment and decrement cancel out on the same document, but the transaction record is created, which would inflate analytics earnings totals.

In `LiveViewer.sendGift`, the host check (`me === stream.host_id`) is only used for access control, not to prevent self-gifting. If the host opens their own viewer URL, they can send gifts that credit themselves and inflate `total_gifts`.

## Partial failure in multi-step transfers

`useTipSend` performs sequential writes: deduct sender → credit recipient → log transaction. If the credit step fails (Firestore rules deny it, or a network error), the sender's balance is already decremented with no compensating write. The same applies to `sendGift` where the sequence is: deduct viewer → credit host → record gift → update stream total. Any failure after the first updateDoc leaves the system in an inconsistent state.

A Firestore batch write (`writeBatch`) could group the debit and credit atomically, though it wouldn't solve the read-for-balance-check problem. The proper solution is `runTransaction` which handles both atomicity and the read consistency.

## Test coverage gaps

Tests exist for all five features with fully mocked Firestore, verifying rendering and basic interaction. Not tested:

- Wallet transfer logic edge cases (insufficient balance path, self-transfer, concurrent calls)
- FinanceDepartment approval/rejection flow (no test file)
- sendGift and buyTicket in LiveViewer
- Error paths when Firestore writes fail mid-transfer (partial debit without credit)
