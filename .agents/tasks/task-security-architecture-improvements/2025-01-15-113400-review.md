# Security hardening, Firestore migration, and UX scaffolding for Aurelix (v2)

This is the second review pass after five issues from v1 were addressed. The messages rule now checks `request.auth.uid in resource.data.participants`, the unread DM query uses a dedicated `unread_counts` collection, Firebase init throws on missing env vars, `push_tokens` has owner-scoped rules, and `call_signals` reads are scoped to participants. The security posture is substantially improved — the remaining issues are rule/query mismatches that will cause runtime permission denials rather than data leaks.

**Watch for:** The actual conversation messages are written to `conversations/{id}/messages/{msgId}` (subcollection), but no Firestore rule covers that path — all message I/O will be denied in production (confirmed). CallProvider's `insertSummaryMessage` writes to a top-level `messages` collection without a `participants` array, violating the create rule (confirmed). The `call_signals` subscription query lacks `to_user` or `from_user` filters matching `request.auth.uid`, so Firestore will reject the query even for legitimate call participants (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The conversation messaging path has a rules/code mismatch: the application uses subcollection `conversations/{id}/messages` but the rules only cover a top-level `messages` collection. Neither path currently works end-to-end — the subcollection has no rule, and the top-level collection's rule demands a `participants` array that no write path supplies.

The call signaling fix from v1 correctly tightened the `call_signals` read rule to `from_user == uid || to_user == uid`, but the `subscribeSignals` query wasn't updated to include a filter that satisfies this rule. Firestore enforces that queries can only return documents the user is allowed to read, and without a matching `where` clause the entire query is rejected at subscribe time. The same problem affects the `getDocs` catch-up query in the callee flow.

The Supabase keys deleted from `.env` remain in git history and should be rotated if still active.

## Conversation messages path vs. rules mismatch

The Conversation page writes and reads from `conversations/{id}/messages/{msgId}`:

```typescript
const msgRef = collection(db, "conversations", id, "messages");
await addDoc(msgRef, { ... });
```

The Firestore rules define `match /messages/{messageId}` at the top level — a completely different path. In Firestore, `conversations/{id}/messages/{msgId}` is a subcollection and requires its own rule. Without one, the default behavior is deny-all.

CallProvider's `insertSummaryMessage` writes to the top-level `collection(db, "messages")` — which does have a rule, but that rule demands `participants` in the document:

```
allow create: if request.auth != null 
  && request.resource.data.sender_id == request.auth.uid 
  && request.auth.uid in request.resource.data.participants;
```

The `addDoc` call doesn't include `participants`:

```typescript
await addDoc(collection(db, "messages"), {
  conversation_id: conversationId,
  sender_id: user.uid,
  content: label,
  created_at: serverTimestamp(),
});
```

The app has two message paths — subcollection (no rule, will deny) and top-level (rule requires participants, not supplied). Neither works in production.

The fix is to choose one canonical path. The subcollection approach (`conversations/{id}/messages`) is the Firestore-idiomatic pattern. Add a nested rule:

```
match /conversations/{conversationId} {
  // existing rules...
  match /messages/{messageId} {
    allow read: if request.auth != null && request.auth.uid in get(/databases/$(database)/documents/conversations/$(conversationId)).data.participants;
    allow create: if request.auth != null && request.auth.uid in get(/databases/$(database)/documents/conversations/$(conversationId)).data.participants;
  }
}
```

Then move `insertSummaryMessage` to use the subcollection path instead.

## Call signals query rejected by security rules

The `subscribeSignals` function subscribes to all signals for a call:

```typescript
const q = query(
  collection(db, "call_signals"),
  where("call_id", "==", callId),
  orderBy("created_at", "asc"),
);
```

With the tightened rule:

```
allow read: if request.auth != null && (resource.data.from_user == request.auth.uid || resource.data.to_user == request.auth.uid);
```

Firestore requires the query to constrain results to documents the user can read. Since neither `from_user` nor `to_user` is filtered to `request.auth.uid`, the query will fail with a permission error at subscribe time — even if all matching documents happen to satisfy the rule.

The practical fix: each participant only needs to receive the *other* party's signals (the code already filters `if (row.from_user === peerId)` client-side). Change the query to `where("to_user", "==", user.uid)` which satisfies the second branch of the OR rule.

For the `getDocs` catch-up query in `acceptIncoming`, the current filter `where("from_user", "==", inc.caller_id)` still doesn't satisfy the rule for the callee (because it proves `from_user == caller`, not `to_user == callee`). Adding `where("to_user", "==", user.uid)` alongside `where("from_user", "==", inc.caller_id)` will satisfy the rule while still getting exactly the needed documents.
