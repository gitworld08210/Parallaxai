# Security hardening, Firestore migration, and UX scaffolding for Aurelix

This change removes a dangerous wildcard Firestore rule (`match /{document=**}`) and replaces it with per-collection rules covering wallets, conversations, messages, calls, notifications, admin audit logs, mutes, blocks, and reports. Firebase config moves from hardcoded values to env vars. CallProvider is rewritten from Supabase-backed signaling to Firestore. Auth.tsx drops its duplicate Supabase profile writes. On the UX side, 264 stub routes now render a ComingSoon page instead of NotFound, an ErrorBoundary wraps the app, push notifications register on native, real-time unread counts land in AppShell, deep linking is configured for Android, and an OfflineIndicator appears when connectivity drops.

**Watch for:** Messages collection is readable by any authenticated user — no conversation-membership check — leaking private DMs (confirmed). The unread-DM query in AppShell uses a dynamic field name (`unread_${uid}`) that requires a composite Firestore index per user, which will fail at runtime for any non-trivial user base (confirmed). Firebase initializes with `undefined` config values when env vars are missing — `console.warn` fires but the app proceeds to call `initializeApp` with an invalid config, which will throw an opaque Firebase error instead of failing clearly (confirmed). `push_tokens` subcollection has no Firestore rule, so token writes will be rejected in production (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The Firestore rules are dramatically tighter than before but leave one significant hole: the `messages` collection grants read access to any authenticated user rather than scoping reads to conversation participants. Because messages are stored as a flat collection (not subcollection of conversations), enforcing membership requires either a denormalized `participants` array on each message document or a Cloud Function relay. The current rule lets any logged-in user query any message.

The signaling documents in `call_signals` accumulate indefinitely with no TTL or deletion path — a storage concern but not a correctness one. More critically, `call_signals` has `read: if request.auth != null`, letting any authenticated user observe signaling data (including ICE candidates containing IP addresses) for arbitrary calls.

The unread-count listeners in AppShell query `conversations` using a dynamic field key (`unread_${uid}`). Firestore cannot create composite indexes on per-user field names at scale; this pattern works during development with the emulator but will throw a "requires an index" error once any query hits the backend with a new uid.

Firebase config validation warns on missing env vars but still calls `initializeApp`, producing confusing runtime errors. The push notification token is written to a `push_tokens/{uid}/tokens/{token}` path that has no corresponding Firestore rule, so the write will be permission-denied on any deploy that doesn't use the emulator.

## Messages collection access control gap

The Firestore rules grant `allow read: if request.auth != null` on the entire `messages` collection. The comment says "requires reading parent conversation" but the rule doesn't actually perform that check — Firestore security rules can't do cross-document reads. Any authenticated user can query `collection("messages")` with any `conversation_id` filter and retrieve messages from conversations they don't belong to.

Since messages live in a separate top-level collection, the conversation-level participant check doesn't cascade. Two viable fixes: restructure messages as `conversations/{id}/messages/{msgId}` subcollections with a wildcard rule inheriting the parent's participant check, or denormalize a `participants` array onto each message document and check `request.auth.uid in resource.data.participants` on read. The subcollection approach is cleaner and avoids unbounded array duplication.

## Unread count query will fail at scale

```typescript
const dmQuery = query(
  collection(db, "conversations"),
  where("participants", "array-contains", user.uid),
  where(`unread_${user.uid}`, ">", 0)
);
```

Firestore requires a composite index for every distinct field combination in a compound query. The field name `unread_${user.uid}` is different for every user, meaning every new uid that signs up would need its own composite index — something that can't be created dynamically. During development this may appear to work (emulator can satisfy queries without indexes) but will throw `FAILED_PRECONDITION: The query requires an index` in production.

The standard pattern is to maintain a `conversation_members` subcollection or a separate `unread_counts/{uid}` document that the client listens to, avoiding per-user field names entirely.

## Firebase initialization with undefined config

```typescript
for (const key of requiredKeys) {
  if (!import.meta.env[key]) {
    console.warn(`[Firebase] Missing environment variable: ${key}`);
  }
}

const app = initializeApp(firebaseConfig);
```

The validation loop warns but execution continues. `initializeApp({ apiKey: undefined, ... })` throws a Firebase internal error like "Firebase: Error (auth/invalid-api-key)" deep in the auth flow rather than at startup. For developers cloning the repo without `.env`, the first visible error will be a cryptic Firebase exception rather than the helpful warning. Converting `console.warn` to `throw new Error(...)` (or at least gating `initializeApp` behind a "all keys present" check) gives a clear, immediate failure.

## Push token Firestore path has no rule

`usePushNotifications` writes to `push_tokens/{uid}/tokens/{tokenValue}`. The Firestore rules file has no `match /push_tokens/{userId}/{document=**}` entry. In production (or any deployment with security rules enforced), this write returns `PERMISSION_DENIED`. The fix is a simple addition:

```
match /push_tokens/{userId}/{document=**} {
  allow read, write: if request.auth != null && request.auth.uid == userId;
}
```

## Call signals readable by any user

The `call_signals` rule allows `allow read: if request.auth != null`, meaning any authenticated user can subscribe to the `call_signals` collection filtered by any `call_id`. The signaling payloads (SDP offers/answers, ICE candidates) reveal IP addresses of call participants and the existence/timing of calls. Scoping reads to `resource.data.from_user == request.auth.uid || resource.data.to_user == request.auth.uid` would close this.

## Credential removal from version control

The diff deletes `.env` (which contained Supabase keys) and adds `.env` to `.gitignore`. Those Supabase keys remain in git history. If those keys are still active, they should be rotated. The Firebase keys that were previously hardcoded in `firebase.ts` are also still in git history — Firebase API keys are client-side identifiers protected by security rules, but the Supabase `anon_key` values should be treated as compromised.
