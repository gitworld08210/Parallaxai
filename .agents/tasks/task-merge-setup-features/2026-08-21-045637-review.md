# Branded loading screen and story progress bar

Two new UI components land in this change: `AppLoadingScreen`, a full-screen branded loading state with a 5-second timeout that redirects to `/auth`, and `StoryProgressBar`, a segmented Instagram-style progress indicator with pause/resume support. The loading screen replaces three inline spinner implementations across `ProtectedRoute` gates and the Suspense fallback. The story bar is standalone with no integration point yet.

**Watch for:** The loading screen's 5s hard redirect to `/auth` fires unconditionally—including for authenticated users on slow networks where the Supabase session fetch takes longer than 5 seconds (confirmed). The `StoryProgressBar` has a stale `onComplete` closure that can fire an outdated callback after pause/resume cycles (likely).

**Verdict**: NEEDS_CHANGES

## High-level view

The loading screen consolidates spinner UX into one branded component. The timeout behavior is the concern: when used as the auth-loading gate, it races against the Supabase session fetch and will redirect authenticated users to `/auth` if that fetch exceeds 5 seconds—then ProtectedRoute re-renders, the user gets bounced back, and the cycle may repeat. The timeout needs to not fire while auth resolution is still in progress.

The story progress bar's `onComplete` callback is captured in the animation effect closure and never refreshed via a ref, meaning a parent that passes a new callback (e.g., after advancing stories) may get the stale version invoked. Additionally, `onComplete` in the dependency array causes the effect to restart on every parent render unless the parent memoizes the callback, visually resetting the progress bar.

<details>
<summary>Issues (4)</summary>

1. **Loading timeout redirects authenticated users** — `AppLoadingScreen` navigates to `/auth` after 5s regardless of auth state. If `supabase.auth.getSession()` takes longer than 5s (cold start, slow network), an authenticated user gets bounced to login. Either disable the timeout in `ProtectedRoute` usage (pass `onTimeout` that's a no-op) or make the timeout aware of auth state.
2. **Stale `onComplete` closure in StoryProgressBar** — The `animate` function captures `onComplete` from the effect dependency array, but React won't re-run the effect when only `onComplete` changes (it's a function reference that changes every render unless the parent memoizes it). Use a ref to hold the latest `onComplete`.
3. **No cleanup of in-flight `onComplete` on index change** — When `currentIndex` changes, the first `useEffect` resets `progress` but the second `useEffect` might have already scheduled a rAF callback that calls `onComplete` for the previous index. The rAF cancellation in cleanup may race with the invocation.
4. **`onComplete` as effect dependency restarts animation** — The animation effect lists `[currentIndex, paused, duration, onComplete]`. Since `onComplete` is typically an unstable reference, the effect re-runs on every parent render, resetting `startTimeRef.current` and restarting progress from `pausedAtRef.current`. This causes visible stutter unless the parent wraps `onComplete` in `useCallback`.

## Loading screen timeout vs auth resolution race

`AppLoadingScreen` starts a 5-second timer on mount. When used inside `ProtectedRoute`, the component mounts while `useAuth().loading` is `true`—meaning the Supabase session fetch is in progress. If that fetch completes within 5 seconds, `loading` flips to `false`, `ProtectedRoute` re-renders away from the loading screen, and the timer is cleaned up. If it doesn't, the timer fires and navigates to `/auth`.

The `AuthProvider` calls `supabase.auth.getSession()` on mount. On a cold Supabase edge function start or slow mobile connection, this can exceed 5 seconds. The result for a slow-but-authenticated user: redirect to login → auth resolves → ProtectedRoute redirects back → possible loop.

```tsx
// AppLoadingScreen.tsx lines 20-28
timerRef.current = setTimeout(() => {
  if (onTimeout) {
    onTimeout();
  } else {
    navigate("/auth", { replace: true });
  }
}, timeoutMs);
```

Fix: in `ProtectedRoute`, pass `onTimeout={() => {}}` or a longer `timeoutMs`, or make the timeout callback check auth state before redirecting.

## StoryProgressBar animation closure

The animation effect depends on `[currentIndex, paused, duration, onComplete]`. The `onComplete` dependency creates a dilemma:

- If the parent passes an inline function, the effect restarts every render, resetting animation progress and causing visual stutter.
- If removed from the dependency array, the closure captures a stale `onComplete` that may reference an outdated story index.

```tsx
<StoryProgressBar
  onComplete={() => goToNextStory(currentStoryId)}
  // ^^^ new reference every render → effect restarts → bar resets
/>
```

The standard fix is a ref:

```tsx
const onCompleteRef = useRef(onComplete);
onCompleteRef.current = onComplete;
// Remove onComplete from deps; in animate(): onCompleteRef.current?.()
```

This keeps the animation stable while always invoking the latest callback.
