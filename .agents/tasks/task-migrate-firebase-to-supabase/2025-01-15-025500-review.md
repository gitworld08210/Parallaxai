# Firebase-to-Supabase migration v3: final review

All five issues from the v2 review have been resolved. Voice messages now include `media_url` and `media_type` in both the insert payload and the `messages` type definition. Messages.tsx reads unread counts from the dedicated `unread_counts` table via a separate query. The recipient wallet credit race, stale-read counters, and remaining `as any` casts on 10 untyped tables are all documented with TODO comments that explain the limitation and the planned server-side RPC fix. No new functional regressions surfaced.

**Watch for:** No blocking issues remain. The documented known limitations (recipient wallet credit, stale counters, untyped tables) are acceptable for initial deployment given the TODO-with-RPC-plan pattern used consistently throughout.

**Verdict**: APPROVED

## High-level view

The wallet sender-side deduction is protected with `.gte('total', amount)` guards across all spend paths. The recipient credit side uses read-then-write without a guard, but every instance carries a TODO comment describing the exact RPC needed. The failure mode (lost credit, not stolen funds) is the less dangerous direction, and the trade-off for shipping without database function deployment is reasonable.

The Messages page realtime subscription triggers a full `load()` refresh on any conversation change, which re-fetches both conversations and unread counts. For high-traffic inboxes this could be expensive; a targeted refresh on the specific conversation row that changed would be more efficient. Non-blocking for initial deployment.

## `user.uid` vs `user.id` inconsistency

The `User` type in AuthProvider defines both `id` and `uid` set to the same value (`supaUser.id`). Several files use `user.uid` (Messages.tsx line 180, CallProvider.tsx, Profile.tsx, ProfileCreation.tsx, CloseFriends.tsx, VirtualWorld.tsx) while most use `user.id`. Functionally correct since `uid === id`, but the `uid` alias exists solely for backward compatibility with Firebase-era code and should be cleaned up in a follow-up refactor pass to avoid confusion for new contributors.
