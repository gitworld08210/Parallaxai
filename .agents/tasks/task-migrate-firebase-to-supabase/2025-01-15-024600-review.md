# Firebase-to-Supabase full-stack migration

This change removes the entire Firebase dependency (Auth, Firestore, Storage) from a React/TypeScript social media platform and replaces it with Supabase for auth and data, and Cloudinary for media uploads. The migration spans 77 files — auth flows, 18+ social/wallet data modules, real-time subscriptions, admin panels, and a WebRTC calling provider. The approach is a direct swap: every Firestore `onSnapshot` becomes a Supabase Realtime channel, every `runTransaction` becomes sequential reads-then-writes, and Firebase Storage uploads become `uploadToCloudinary` calls. The build passes, TypeScript compiles cleanly, and no Firebase imports remain in production code.

**Watch for:** Loss of atomicity in wallet/coin operations (confirmed — race conditions enabling double-spend). Stale-read increments on view/comment counts (confirmed). `as any` type casts across ~40 files suppress compile-time schema validation (confirmed). Conversation `markRead` overwrites entire JSONB column instead of patching one key (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

Auth migrates cleanly to Supabase's session model. Google OAuth moves from popup to redirect (correct for mobile web), and `createProfileInSupabase` fires on every `onAuthStateChange` event, so new Google users get a profile on first redirect-back without a gap.

Every wallet mutation (tips, gift sends, ticket purchases, admin coin approvals) previously ran inside a Firestore `runTransaction`. The migration replaces these with sequential `select` → `update` steps with no lock between them, making concurrent double-spend possible. This is the single largest functional regression.

The entire data layer is cast through `as any` because the migrated tables aren't properly reflected in the generated `Database` type. Incorrect column names or wrong types won't surface until runtime.

Counter increments (view count, comment count) use the client-side stale value rather than a server-side atomic increment, losing updates under concurrency.

Real-time subscriptions are consistently cleaned up via `supabase.removeChannel(channel)` across all components. The tables must be added to the Supabase Realtime publication for subscriptions to receive events — if any are missing, the channels will silently produce nothing.

<summary>Issues (6)</summary>

1. **Wallet race condition** — All wallet transfers (tips, gifts, ticket purchases, admin approvals) use sequential read-then-write without locking. Move to a Supabase RPC that does `UPDATE wallets SET total = total - $amount WHERE user_id = $sender AND total >= $amount RETURNING total`.
2. **View/comment count lost updates** — `view_count` and `comment_count` are set to `clientValue + 1` instead of a server-side `SET col = col + 1`. Use a Supabase RPC for atomic increment.
3. **Pervasive `as any` suppresses type safety** — ~40 files cast Supabase queries through `as any`, hiding schema mismatches. Add the migrated tables to the generated Database type or create a typed wrapper.
4. **Conversation unread update overwrites JSONB** — `markRead` writes `{ unread_counts: { [user.id]: 0 } }` which replaces the entire column, wiping the other participant's count. Use a JSONB merge via RPC.
5. **signupChecks `registerEmailAccount` non-atomic increment** — The read-then-upsert of `email_accounts.count` can miss concurrent signups, allowing bypass of the 3-accounts-per-email limit.
6. **ResetPassword assumes active session** — `supabase.auth.updateUser({ password })` requires an active session established from the recovery token. If the user submits before `detectSessionInUrl` processes the hash asynchronously, the call fails. Guard the form behind a session check.

## Wallet atomicity lost in migration

The new code in `useTipSend.ts`, `LiveViewer.tsx` (ticket purchase and gift send), `FinanceDepartment.tsx`, and `ApprovalsInbox.tsx` follows the same pattern:

```ts
// 1. Read sender balance
const { data: senderWallet } = await supabase.from('wallets').select('total').eq('user_id', senderId).single();
const currentBalance = senderWallet?.total || 0;
// 2. Check balance client-side
if (currentBalance < amount) throw new Error("Insufficient balance");
// 3. Write new balance
await supabase.from('wallets').update({ total: currentBalance - amount }).eq('user_id', senderId);
```

Between steps 1 and 3, another request can read the same balance and both deductions succeed, driving the balance negative. On the recipient side, if two gifts arrive simultaneously, one credit is lost (both read `total=100`, both write `total=100+gift`).

The fix is a Supabase RPC that performs `UPDATE wallets SET total = total - $amount WHERE user_id = $sender AND total >= $amount RETURNING total`, which is atomic and prevents negative balances. The transaction log insert can happen afterward since it's append-only.

## View count and comment count stale-read increment

In `PostCard.tsx`:
```ts
supabase.from('posts').update({ view_count: (post as any).view_count ? (post as any).view_count + 1 : 1 }).eq('id', post.id)
```

This uses the client-side `post.view_count` value, which may be stale. Two concurrent viewers both read `view_count=5` and both write `6`. The same pattern in `CommentSheet.tsx` reads `comment_count` from the database, then writes `currentCount + 1` — still vulnerable between the read and write.

## Pervasive `as any` casts suppress type checking

Nearly every Supabase query is written as:
```ts
await supabase.from('posts' as any).select('*').eq('user_id', userId) as any;
```

The `Database` type in `src/types/supabase.ts` was extended with 28 new table definitions, but the table names used in `.from()` calls apparently don't match what TypeScript expects from the generated types. The `as any` makes every query effectively untyped — a renamed column, missing field, or wrong filter won't surface until runtime.

## Conversation `markRead` overwrites all unread counts

In `Conversation.tsx`:
```ts
await supabase.from('conversations').update({
  [`unread_counts`]: { [user.id]: 0 },
  last_read: true
}).eq('id', id);
```

If `unread_counts` is a JSONB column storing per-user counts like `{ "user_a": 3, "user_b": 0 }`, this overwrites the entire column with `{ "current_user_id": 0 }`, erasing the other participant's unread count. The Firestore version used a dot-path update (`unread_counts.${user.id}`) which only patched one nested field. The correct Supabase approach is a JSONB merge via RPC: `UPDATE conversations SET unread_counts = unread_counts || jsonb_build_object($user_id, 0) WHERE id = $id`.

## ResetPassword session timing (possible)

`ResetPassword.tsx` parses the hash fragment for `access_token` and `type=recovery`, then on form submit calls `supabase.auth.updateUser({ password })`. For `updateUser` to work, the client must have an active session. Supabase's `detectSessionInUrl: true` (set in the client config) should automatically pick up the recovery token from the URL hash and establish a session — but this happens asynchronously via the client constructor. The component's `useEffect` runs synchronously to parse the hash and enable the form. If the user submits before `onAuthStateChange` fires with the recovery session, `updateUser` will fail with "Auth session missing."

The mitigation is to guard the submit button behind a session check (`await supabase.auth.getSession()`) or explicitly call `supabase.auth.setSession()` with the parsed tokens.

## Realtime publication requirement

Supabase Realtime requires each table to be added to the `supabase_realtime` publication. The migration introduces realtime subscriptions on: `notifications`, `unread_counts`, `comments`, `wallets`, `messages`, `conversations`, `calls`, `call_signals`, `live_chat`, `live_gifts`, `live_streams`, `coin_topups`, `verification_requests`, `virtual_world_applications`. If any of these tables aren't in the publication, the corresponding channels will silently receive no events — subscriptions won't error, they just won't fire.
