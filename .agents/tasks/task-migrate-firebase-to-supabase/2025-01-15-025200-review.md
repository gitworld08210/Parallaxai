# Firebase-to-Supabase migration v2: post-fix review

The six issues from the first review have been addressed with varying degrees of completeness. The wallet sender-side race condition now has a `.gte()` guard, the conversation unread overwrite uses a separate table, and the ResetPassword form gates behind a session check. View/comment count and signupChecks non-atomicity are documented as known limitations. The `as any` casts are reduced for tables with type definitions, though ~135 result-level casts persist across the diff. Two new functional regressions surfaced: voice messages silently drop their audio attachment, and the Messages list reads unread counts from the old JSONB path that's no longer written to.

**Watch for:** Voice messages store no media (confirmed). Messages page unread badges never reflect new reads (confirmed). Recipient wallet credits remain non-atomic under concurrency (confirmed). `like_count` and `total_gifts` updates use local state as the write value (confirmed — same class as the acknowledged view_count issue).

**Verdict**: NEEDS_CHANGES

## High-level view

The sender-side deduction guard (`.gte('total', amount)`) prevents negative balances on the sending wallet, which was the most dangerous failure mode. However, the recipient credit path still does a read-then-write for all wallet operations (tips, gifts, ticket sales, admin approvals), meaning concurrent gifts to the same host can lose credits. The asymmetry — sender protected, recipient not — is a residual gap worth closing with the same pattern or an RPC.

The unread_counts table migration in Conversation.tsx is correct, but Messages.tsx was not updated to read from it. It still dereferences `conversations.unread_counts?.[user.id]`, a JSONB field that is never written after this change. The result: unread badges in the message list are permanently stale.

The `sendVoice` function in Conversation.tsx accepts a `mediaUrl` parameter but the insert payload omits `media_url` and `media_type` entirely (and the `messages` type definition lacks these columns). Voice messages arrive as empty-content text messages.

The `like_count` update in PostCard and `total_gifts` in LiveViewer follow the same stale-read pattern as `view_count` — using an optimistic local variable rather than the database value. Given that view_count is already documented as a known limitation pending an RPC, these are in the same category but should be explicitly acknowledged.

<details>
<summary>Issues (5)</summary>

1. **Voice messages drop media** — `sendVoice` in Conversation.tsx ignores the `mediaUrl` parameter; the insert has no `media_url` or `media_type` field. Add these columns to the `messages` table type and include them in the insert payload.
2. **Messages unread badge reads orphaned JSONB** — Messages.tsx line 87 reads `d.unread_counts?.[user.id]` from the `conversations` table, but writes now go to the separate `unread_counts` table. Either join `unread_counts` in the Messages query or maintain backward-compatibility by still writing to both.
3. **Recipient credit lost under concurrency** — All wallet recipient credits (tips, gifts, tickets, admin approvals) use `select total → update total + amount` with no guard. Two simultaneous gifts to the same host will both read the same balance and one credit is lost. Apply the same `.gte()` pattern or use an RPC for atomic `SET total = total + $amount`.
4. **`like_count` and `total_gifts` stale-read writes** — PostCard updates `like_count` using the local `likes` state variable; LiveViewer updates `total_gifts` from `stream.total_gifts` in component state. Concurrent likes or gifts lose updates. Same class as view_count — document as known limitation or batch into the planned RPC.
5. **Remaining `as any` on 10 untyped tables** — Tables `close_friends`, `post_collaborators`, `platform_settings`, `sup_tickets`, `login_events`, `engagement_events`, `platform_activity`, `message_passcodes`, `story_sticker_responses`, `organization_settings` still use `from('name' as any)`. Low severity but worth tracking for future type generation passes.

## Voice messages silently lost

In `Conversation.tsx`, `sendVoice` is called with a `mediaUrl` string but the message insert ignores it:

```ts
const sendVoice = async (mediaUrl: string) => {
  if (!user || !id) return;
  await supabase.from('messages').insert({
    conversation_id: id,
    sender_id: user.id,
    content: "",
  } as any);
  // mediaUrl never used
};
```

The `messages` type in `supabase.ts` only defines `id`, `conversation_id`, `sender_id`, `content`, `created_at` — no `media_url` or `media_type` columns. The feature is structurally broken: the database schema, the TypeScript type, and the insert all lack the media fields. The conversation's `last_message_text` is set to "🎤 Voice message" but the actual audio is unreachable.

## Messages page reads orphaned unread source

`Messages.tsx` line 87:
```ts
unread: d.unread_counts?.[user.id] || 0,
```

This reads from a `unread_counts` JSONB column on the `conversations` row. After the fix for issue #4, `Conversation.tsx` writes to a separate `unread_counts` *table* via upsert. Meanwhile `AppShell.tsx` correctly reads from the `unread_counts` table (querying rows where `count > 0`). The Messages list page is now inconsistent: it will always show 0 unread (or whatever stale value exists in the JSONB) regardless of actual state.

## Recipient wallet credit remains vulnerable

The `.gte('total', amount)` guard on sender deductions is effective — if balance drops below the required amount between read and write, the update matches zero rows and the function throws. But the corresponding recipient credit:

```ts
const { data: recipientWallet } = await supabase
  .from('wallets').select('total').eq('user_id', recipientId).maybeSingle();
if (recipientWallet) {
  await supabase.from('wallets')
    .update({ total: recipientWallet.total + amount })
    .eq('user_id', recipientId);
}
```

Two concurrent tips/gifts to the same recipient both read `total=100`, both write `total=100+gift`. One credit is lost. This pattern repeats in `useTipSend.ts`, `LiveViewer.tsx` (buyTicket and sendGift), `FinanceDepartment.tsx`, and `ApprovalsInbox.tsx`. The fix is the same RPC approach: `UPDATE wallets SET total = total + $amount WHERE user_id = $recipient RETURNING total`.

## Stale-read counters beyond view_count

`PostCard.tsx` toggleLike:
```ts
await supabase.from('posts').update({ like_count: likes + 1 }).eq('id', post.id);
```

`likes` is local component state (initialized from `post.like_count`, then optimistically toggled). Under concurrent likes, both users read the same count from state and write the same value.

`LiveViewer.tsx` sendGift:
```ts
await supabase.from('live_streams').update({ total_gifts: (stream.total_gifts || 0) + g.cost_coins }).eq('id', stream.id);
```

`stream` is loaded once on mount. During an active stream with many gifts, each viewer's local `stream.total_gifts` diverges from the actual database value.

These are the same class as the acknowledged view_count/comment_count limitation but aren't yet documented with TODO comments.
