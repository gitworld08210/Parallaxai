# Performance and quality infrastructure for Parallax social app (v2)

This change adds eight features to Parallax: Vite bundle splitting, infinite scroll with Firestore cursor pagination, client-side image compression and Cloudinary URL transforms, Zod v4 form validation via react-hook-form, error reporting to Firestore, client-side rate limiting, i18n with English/Hindi, and PWA support via a service worker. All seven issues from the v1 review have been properly addressed — the `loadMore` reference is now stable via `hasMoreRef`, the service worker uses network-first for hashed assets with cache trimming, the `zodResolver` builds nested `FieldErrors`, alpha-capable images export as WebP, `checkRateLimit` differentiates toast messages, the Discover page gates the observer behind `initialLoadDoneRef`, and stale caches are evicted via `trimCache`.

**Watch for:** The `trimCache` function uses FIFO eviction based on `cache.keys()` insertion order rather than LRU, so frequently-accessed assets cached early can be evicted before rarely-used assets cached later (possible). At `MAX_ASSET_CACHE_SIZE=50` this is unlikely to cause user-visible issues during normal browsing.

**Verdict**: APPROVED

## High-level view

All seven v1 issues have been resolved. The `useInfiniteFirestore` hook reads `hasMore` from a ref and `loadMore`'s `useCallback` depends only on `[baseQuery, pageSize]`, eliminating observer teardown cycles. The service worker switched to network-first for navigation and hashed assets with `trimCache(CACHE_NAME, 50)` after each write. The `zodResolver` walks the issue path array to build nested error objects. Image compression outputs WebP for alpha-capable formats (PNG, GIF, WebP source types).

The FIFO trimming strategy is the one minor remaining observation. The Cache API's `keys()` returns entries in insertion order, so `trimCache` evicts the oldest-inserted entries regardless of access frequency. A heavily-used JS chunk cached on first visit could theoretically be evicted before a rarely-hit CSS file cached later. The 50-entry cap provides enough headroom that this is unlikely to matter — a Vite build typically produces 10–20 chunks, well under the limit.

## Service worker trimming mechanics

The `trimCache` function runs after each asset cache write:

```js
async function trimCache(cacheName, maxSize) {
  const cache = await caches.open(cacheName);
  const keys = await cache.keys();
  if (keys.length > maxSize) {
    const excess = keys.length - maxSize;
    for (let i = 0; i < excess; i++) {
      await cache.delete(keys[i]);
    }
  }
}
```

Because the Cache API returns keys in insertion order and the function deletes from the front, this is FIFO. A content-hashed chunk cached on the first page load (e.g., `vendor-react-Xk3f.js`) will be evicted before a chunk cached later, even if the react chunk is loaded on every navigation. The cache entry is re-inserted after each network-first fetch though, so in practice, any asset that the browser requests regularly will be re-cached after eviction on the very next load — the user pays one extra network request for that asset, once.

The network-first strategy means this eviction has no correctness impact — it only affects offline availability. An asset evicted from cache simply won't be available offline until re-fetched.
